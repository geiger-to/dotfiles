# Comments

Do not write comments. No exceptions.

This includes docstrings, JSDoc, rustdoc, and every other doc-comment format — even when the file around it is full of them. It includes restating what the code does, section headers, step-by-step narration, notes explaining a change I asked for, and TODO/FIXME.

The code explains itself. If it needs a comment to be understood, rename things or restructure it.

If I explicitly ask for a comment, write that one. Don't delete comments already in code you're editing unless I say so.

# Writing

Applies to docs, READMEs, commit messages, UI copy, and error messages.

## Voice and tone

- Voice: trustworthy, confident, empowering, practical, and clear. Keep it the same everywhere.
- Tone: match the moment. Be direct and serious for errors and warnings. Be helpful and encouraging for onboarding and setup.

## Rules

- Readability: use plain language at a grade 7 reading level. Avoid jargon, idioms, and long, dense blocks of text.
- Consistency: pick one exact term for each concept or action and stick with it. Don't swap in synonyms.
- Action: start calls to action with a strong, active verb. Break complex tasks into clear steps in order.
